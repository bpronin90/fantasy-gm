# P2.4 outcome evaluation and deterministic research

Implemented locally using the existing SQLite Decision Ledger, immutable Research Packs, public CSV collectors, and standard-library Python. No live n8n operation, private input, Yahoo call, paid AI inference, or transaction is part of this delivery. The new workflow JSON is a new, inactive draft, not an export or replacement of a working workflow.

## Evaluate a recorded recommendation

Use a previously recorded `decision_id` and its existing private `decisions.sqlite`. No recurring roster/waiver imports are introduced. A recommendation includes the original snapshot, settings, assessments, evidence, report, and timestamps. `outcomes.load_decision` reads it without modifying it and verifies the frozen pack/snapshot hashes and, for decisions recorded with a `record_hash`, the whole decision. Decisions recorded before `record_hash` existed are accepted but their outcomes are labelled `decision_integrity: legacy_unverified`. Both CLIs refuse a `--ledger` inside the repository unless it is under ignored `data/private/`.

```sh
# Prepare the separate cutoff-only view BEFORE inspecting results.
# Output contains private material: redirect only to ignored/private storage.
python3 -m src.fantasy_gm.outcomes \
  --ledger data/private/weekly/decisions.sqlite --decision-id DECISION_ID \
  --as-of CURRENT_TIME_WITH_TIMEZONE --reasoning-view \
  > data/private/reasoning-view.json

# User-initiated live public-results collection, then deterministic evaluation.
python3 -m src.fantasy_gm.outcomes \
  --ledger data/private/weekly/decisions.sqlite --decision-id DECISION_ID \
  --as-of CURRENT_TIME_WITH_TIMEZONE

# Offline replay accepts preserved collector artifacts, without network access.
python3 -m src.fantasy_gm.outcomes \
  --ledger data/private/weekly/decisions.sqlite --decision-id DECISION_ID \
  --as-of ARTIFACT_EVALUATION_TIME --artifacts data/private/actuals.json \
  --review data/private/reasoning-review.json
```

The CLI emits only an outcome ID, status, regret, and classification. Private full results remain in the ledger. The artifact object is keyed by `stats`, `schedule`, optionally `team_stats`; values use the existing collector format (`rows`, URL, provider, fetched_at, SHA256). Live collection uses actual collection times and requires a current cutoff. Historical replay uses the recorded artifact times; it never fetches today and pretends the evidence existed earlier. The evaluator rejects future or >24-hour-old artifacts relative to the evaluation time.

Player results join verified GSIS identities and exact season/type/week; defenses join team/season/week. Duplicate rows, absent scoring columns, unverified identities, missing games, and unfinished games remain explicit gaps. The schedule must report `status: final` or a nonempty final `result` with both scores; a score alone is insufficient. This is source-reported completion, not independently verified NFL certification. Corrected public data can still change it.

Scoring uses the **recorded** `league_settings.scoring` exact stat-column coefficients, including fractional yards and negative turnovers. It never consumes provider fantasy-point totals or invents PPR defaults. Every nonzero coefficient needs an observed finite value. Optional recorded `scoring_bonuses` rules contain exactly `stat`, `min`, `max` (exclusive, nullable), and `points`; multiple applicable bonuses add. This supports yardage bonuses and points-allowed intervals when the source actually supplies the matching statistic. For DEF and K, `scoring_by_position` must explicitly supply that position’s object with `scoring`, `missing_rules` and optional `scoring_bonuses`; offensive team totals are never automatically scored as defense production. Optional offensive position scopes use the same contract; conflicting multi-position scopes block scoring. No Yahoo default tiers, DEF aggregate mapping, distance-based kicking rules, or missing stats are guessed. Missing/unsupported rules require an explicit `missing_rules` entry and block a complete evaluation. P2.4 does not retrospectively amend a decision's scoring rules. Calculations preserve ten decimal places for numeric stability; no unrecorded Yahoo rounding policy is assumed.

Missing player rows never mean zero. Optional `--participation` supplies preserved, sourced NFL participation facts, not a roster import: each DNP fact needs subject, game_id, season, season_type, week, status `dnp`, HTTPS source_url, revision and fetched_at. Only an explicitly sourced DNP after source-reported completion can yield zero. Conflicting DNP/stat rows stay unresolved. An injury report alone does not establish final participation. No stable automatic inactive-announcement feed is claimed.

## Historical lineup comparison

The engine reconstructs all active slots from the original configuration, including separate `FLEX:1` and `FLEX:2`. It searches the complete feasible player sets rather than only the five candidate lineups saved in the original report. A player appears at most once, must have recorded slot eligibility, and must have been on the recorded roster. IR/IR+ and byes are unavailable. Players known out/inactive at the cutoff are excluded before kickoff. Later injuries and DNPs affect results, not historical eligibility.

A kicked-off starter stays in its original slot; a kicked-off bench/reserve player cannot enter. Unknown kickoffs or eligibility stop a definitive optimum. This models the existing foundation's individual-player kickoff locks; other lock policies need explicit support before being marked verified. Equal FLEX slots use the original roster order for stable slot numbering. The bounded bitset search reports a limit error instead of silently approximating.

Each evaluation records:

- Recommended points and the best feasible complete lineup's actual points.
- `lineup_regret`: best feasible points minus recommended points (zero means tied for best).
- `points_gained_lost`: recommended points minus the supplied snapshot's **recorded starting lineup**, when that baseline is legal and fully scored.
- Actual rows, game states, source revisions, original scoring, gaps, uncertainty, and decision hash.

These are retrospective comparisons of **recorded recommendations**, not actual submitted Yahoo lineups. Alternatives are **recorded roster players**, not verified waiver opportunities. Yahoo submission/adoption remains unknown. A verification section is an original attestation, not a new API check; missing/future checks and provisional archives retain explicit uncertainty. Results under manually supplied assumptions are conditional. Unknown league information is never filled in.

## Review reasoning without hindsight

Outcome arithmetic cannot prove that a thesis was justified. By default the reasoning judgment is `insufficient`, even when all fantasy points are known. User-initiated Codex review uses `reasoning_view(record)`: frozen context, assignments, assessments, coverage, and evidence available by the original cutoff. It excludes outcome stats, newer research and late/undated evidence. A future kickoff is an event time, so it is allowed when the schedule was fetched before cutoff. Other observed, published (when known), and fetched times must be no later than cutoff. Unknown publication time is retained; the preserved fetch establishes availability.

A review JSON contains `view_hash` (the canonical `research.digest(view)`), `cutoff_only: true`, `blinded_to_results: true`, `judgment` (`good`, `poor`, `insufficient`), nonempty `rationale`, original cutoff-safe `evidence_ids`, and optional `error_tags` such as `ignored_counterargument`, `small_sample`, `role_assumption`, or `overconfidence`. The attestation is a human workflow requirement, not proof that a reviewer has never seen a result. Review reasoning first. No code can certify psychological blindness. Original coverage gaps, excluded evidence, blockers, and provisional archives conservatively retain an insufficient judgment. A changed view/hash or citations outside the original view are rejected.

With a defensible review and verified recorded rules, zero regret is labeled a good outcome; positive regret is labeled a bad outcome. Combine that result with the independent good/poor reasoning judgment for the four requested categories. “Bad outcome” here means hindsight lineup regret, not negligence or a prediction-quality verdict. Missing results, uncertainty, or a missing reasoning review yields “insufficient evidence to judge.” Scheduled postgame runs retain a previously recorded cutoff-only review when appending corrected results; they never generate a new reasoning judgment.

## Immutable revisions and historical findings

`outcomes` is an append-only table alongside the existing `decisions` table. Every record links `decision_id` plus a hash of the complete original record. It has a content-addressed `outcome_id`, evaluator version, as_of, prior `supersedes` ID, and initial/reassessment state. SQL triggers reject outcome updates/deletes. Existing decision payloads are never updated or deleted. Corrections, completed games, or new reviews append records. Replays matching the latest content reuse its outcome ID; a fetch-time-only refresh does not create a revision. A correction reverting A → B → A appends a new linked A revision so the latest view remains correct. Original incomplete/corrected records remain inspectable. Revisions older than the latest recorded evaluation are rejected.

`history(ledger, request)` selects the latest evaluation per decision available at the new cutoff and filters league/team/test-versus-real context. It exposes linked evaluations, recurring error tags, evidence-gap counts, and confidence observation/decision-regret counts. It counts each decision once despite stat revisions. This is descriptive history with potentially overlapping recommendations, not confidence calibration, a machine-learning model, or automatic self-improvement.

Scheduled refreshed packs embed these findings in their hash. The existing report renderer displays the summaries, and the Codex prompt requires review of the linked decisions before applying a finding. For other user-initiated pack builders, attach `history(...)` before computing `pack_id`. Do not retrofit history into old packs. Changed analysis requires a new report/decision, preserving the original record.

## Deterministic jobs and prepared Research Packs

```sh
python3 -m src.fantasy_gm.automation \
  --ledger data/private/weekly/decisions.sqlite --job data/private/research-job.json
```

The private job JSON has `task` (`research`, `pregame`, `postgame`), `interval_seconds` (300–86400), `decision_ids` (existing ledger IDs), and `context` with league_id, team_id, season, season_type, week, mode matching all decisions. It contains no new roster or waiver import. This is an explicit small single-user job scope; selecting future decision IDs and weeks remains a deployment/configuration responsibility until a synchronized decision source is connected.

| Task | Deterministic work prepared for scheduling |
| --- | --- |
| research | Existing players, schedule and weekly-stat collectors; weekly NFL rosters; optional public injury feed; coverage/freshness checks; frozen pack and change notices |
| pregame | Same collectors, with 15-minute schedule freshness; research refresh for Codex; kickoff/injury/identity/roster changes and evidence gaps flagged |
| postgame | Schedule, player/team statistics; incomplete-result detection; outcome append; correction reassessments; preserves an existing reasoning review |

NFL roster monitoring reports team/identity changes; it never changes fantasy ownership or eligibility. The optional injury adapter preserves `report_status`/`date_modified` and the original row. A timestamp without a timezone remains unknown. Missing/current-season unavailable injury reports and blank statuses remain gaps. Monitor observations never attest official active/inactive verification. Official final injury/news/matchup review remains a user-initiated research step. Scheduled packs are explicitly marked for final review; stale recorded rosters cannot become current merely because public NFL data was refreshed. No new recommendation is automatically issued.

Collection reuses `research.collect` and its bounded size/time and three fetch attempts. Supplemental weekly-roster/injury schemas extend that same downloader/parser. A job key includes configuration, time bucket and worker version. SQLite serializes concurrent workers, reuses successful windows, and stores up to three visible failed attempts per window. The worker retains private pack/change/failure payloads in `research_jobs`, emits a minimal status, and exits nonzero on source/calculation failure. There is no stale-cache success fallback. A missing player/week is a coverage gap even when HTTP collection succeeds. No notification is sent externally. n8n must surface the worker's failure exit after authorized deployment.

Postgame pending outcomes are saved in the job attempt before append. `complete_outcomes` replays them idempotently after a crash; rerunning the CLI completes a previously successful window's pending records. Process death before the job transaction commits rolls it back. Holding the SQLite transaction across bounded collection is intentional for one local worker; this is not a distributed queue. Full source artifacts stay private and may grow; retention/deletion is not automated or authorized here.

The draft polls research hourly, pregame every 15 minutes, and postgame every six hours. These are proposed timers, not kickoff-aware calendar guarantees; narrow the enabled pregame window/scope during deployment to avoid unnecessary polling. Job interval_seconds must match the selected polling cadence. No schedules have been activated.

## Source contracts and integration limits

Checked against primary documentation, not a live artifact/execution test: the [weekly roster loader](https://github.com/nflverse/nflreadr/blob/main/R/load_rosters_weekly.R) supplies the weekly CSV location; the [injury dictionary](https://nflreadr.nflverse.com/articles/dictionary_injuries.html) identifies status and modification fields. The [publisher schedule](https://nflreadr.nflverse.com/articles/nflverse_data_schedule.html) describes update/correction windows; these do not establish current-season completeness or an SLA. Source retrieval, parser behavior and missing-feed failures require an authorized real-environment test before scheduling.

Yahoo approval still blocks verified synchronization of scoring/eligibility/lock settings, actual roster history, submitted lineups, waiver availability, acquisition counts, claims and adoption. No OAuth, scraping, browser automation, recurring copy/paste workflow or automatic transaction is added. After approval, a Yahoo adapter should supply verified snapshots and separate adoption/submitted-lineup facts; it must not mutate original recommendation/evaluation records. NFL results collection and recorded-snapshot evaluation operate independently today.
